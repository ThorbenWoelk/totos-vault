### Sentinel object

**Tags:** Python, API design

**In one line:** A sentinel object is a unique marker that distinguishes a missing value from a legitimate value such as `None`.

**Definition:** Some functions need to tell whether an argument was omitted or explicitly supplied. A dedicated object created with `object()` provides a marker that ordinary input values will not accidentally match. Compare it using `is`, which checks identity, rather than `==`, which can invoke custom equality behavior.

**Where it shows up:** Optional function arguments, dictionary lookups, configuration merging, and partial updates where “leave unchanged” differs from “clear this field.”

**Example:** Here, omitting `name` preserves the existing setting, while passing `None` explicitly clears it.

```python
MISSING = object()
settings = {"name": "Thorben"}

def update_name(name=MISSING):
    if name is not MISSING:
        settings["name"] = name

update_name()       # Keeps "Thorben"
update_name(None)   # Stores None
```

**Related concepts:** Builds on object identity and complements nullable values. It serves a similar purpose to an explicit “missing” variant in a tagged union.

**Keep in mind:** Give absence its own representation whenever `None` already means something; reuse the same sentinel instance for both the default and the identity check.

### Bulkhead isolation

**Tags:** software architecture, resilience

**In one line:** Bulkhead isolation gives different workloads separate resource budgets so one overloaded part cannot consume everything.

**Definition:** Like watertight compartments in a ship, bulkheads limit how far a failure can spread. In software, you reserve or cap resources such as worker threads, connections, or concurrent requests for particular dependencies or customers. When one compartment fills up, its requests wait within a bounded queue or fail quickly, leaving capacity available elsewhere.

**Where it shows up:** Separate connection pools for external services, dedicated worker pools for background jobs, and per-tenant concurrency limits in shared applications.

**Example:** A checkout service allows at most `20` concurrent payment calls and `5` recommendation calls. If recommendations stall, they occupy only their five slots; payment calls can still use theirs. A single shared pool of `25` slots could instead become entirely occupied by stalled recommendation requests.

**Related concepts:** Circuit breakers stop calls to unhealthy dependencies; timeouts release resources; backpressure slows incoming work. Bulkheads complement all three by dividing capacity into independent budgets.

**Keep in mind:** Isolate the resource that actually gets exhausted: separate queues alone will not protect you if they still compete for the same saturated worker pool.

### Move semantics

**Tags:** Rust, memory management

**In one line:** Move semantics transfer ownership of a value, so its previous owner can no longer use that value.

**Definition:** In Rust, assigning a value that does not implement `Copy`, or passing it to a function by value, transfers ownership. The compiler rejects subsequent use through the old binding, preventing two owners from independently freeing the same resource. Moving a `String` transfers its ownership without duplicating the text stored on the heap. Types implementing `Copy`, such as `u32`, remain usable after assignment. [Rust ownership guide](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html)

**Where it shows up:** Passing buffers into processing functions, inserting owned values into collections, and returning results from functions.

**Example:** Ownership changes at the assignment; uncommenting the last line produces a compiler error.

```rust
let original = String::from("hello");
let transferred = original;
println!("{transferred}");
// println!("{original}"); // Error: use after move
```

**Related concepts:** Borrowing provides temporary access without transferring ownership. `Clone` explicitly creates another value; `Copy` permits implicit copying. Ownership and `Drop` connect resource cleanup to a value's lifetime.

**Keep in mind:** Borrow when the caller should retain ownership; move when the recipient should take responsibility for the value.

### Watermark

**Tags:** data engineering, stream processing

**In one line:** A watermark estimates how far a streaming pipeline has progressed through the timestamps of its events.

**Definition:** Events can arrive out of order, so a pipeline needs a way to decide when a time window is probably complete. A watermark represents the point in event time before which the system expects no more events. Depending on the source, this can be an estimate rather than a guarantee. Events arriving behind that point are late; the pipeline’s configured policy determines whether they can still update results. [Apache Beam guide](https://beam.apache.org/documentation/programming-guide/#watermarks-and-late-data)

**Where it shows up:** Windowed counts, streaming dashboards, and event-time triggers in Apache Beam pipelines.

**Example:** You count purchases in the window `[10:00, 10:05)`. When the watermark reaches `10:06`, an event-time trigger can emit that window’s count. A purchase timestamped `10:03` arriving afterward is late, even if it just reached your server; accepting it requires a suitable late-data policy.

**Related concepts:** Event time describes when something happened; processing time describes when code handled it. Windows group events, while triggers decide when to publish results.

**Keep in mind:** Treat “window emitted” and “window can never change again” as separate decisions.

### Exhaustiveness checking

**Tags:** TypeScript, type safety

**In one line:** Exhaustiveness checking makes the compiler flag cases your code forgot to handle.

**Definition:** When a value has a finite set of possible variants, each branch handles part of that set. In TypeScript, handling every variant narrows the remaining value to `never`, a type representing no possible value. Assigning that remaining value to a `never` variable turns an omitted case into a compile-time error. [TypeScript handbook](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#exhaustiveness-checking)

**Where it shows up:** Reducers handling actions, UI components rendering request states, and message handlers switching over event types.

**Example:** A function switches over `status: "idle" | "loading"`, returning from each case. Its `default` branch contains `const unhandled: never = status;`. Adding `"failed"` to the union now makes that assignment fail until you handle the new state. A default branch that simply returns `"Unknown"` would silently accept the omission.

**Related concepts:** Builds on union types, control-flow narrowing, and the `never` type; discriminated unions extend the approach to variants carrying different data.

**Keep in mind:** Make missing cases fail during development, but still validate external input: compile-time coverage cannot guarantee that incoming JSON matches your declared types.

### Temperature

**Tags:** AI, text generation

**In one line:** Temperature controls how strongly a language model favors its most likely next tokens when sampling.

**Definition:** Before sampling, the model’s raw scores, called logits, are divided by a positive temperature `T` and converted into probabilities with `softmax`. Values below `1` concentrate probability on higher-scoring tokens; values above `1` flatten the distribution, giving less likely alternatives more opportunity. Temperature changes token selection without changing the model’s learned weights or adding knowledge.

**Where it shows up:** Text-generation settings in model servers, chatbot configurations, and experiments comparing output diversity.

**Example:** Suppose two candidate tokens have logits `2` and `1`. At `T=1`, their probabilities are approximately `73%` and `27%`; at `T=0.5`, they become `88%` and `12%`. The favorite stays the same, but sampling it becomes more likely. In Hugging Face Transformers, temperature affects generation only when sampling is enabled with `do_sample=True`. [Transformers documentation](https://huggingface.co/docs/transformers/internal/generation_utils#transformers.TemperatureLogitsWarper)

**Related concepts:** `softmax` turns scores into probabilities; top-k and top-p sampling restrict eligible candidates; greedy decoding always selects the highest-scoring token.

**Keep in mind:** Lower temperature increases consistency, but a consistently selected answer can still be wrong.

### Context manager

**Tags:** Python, resource management

**In one line:** A context manager defines setup and cleanup around a block of Python code.

**Definition:** The `with` statement calls a manager’s `__enter__()` method before running its block, then calls `__exit__()` when the block finishes. Once entry succeeds, exit runs even when the block raises an exception or returns early. The manager decides what cleanup means, such as closing a file or releasing a lock. Its exit method can also suppress an exception by returning a truthy value. [Python reference](https://docs.python.org/3/reference/compound_stmts.html#the-with-statement)

**Where it shows up:** File handling, lock acquisition, temporary directories, and database transaction scopes.

**Example:** The file closes when execution leaves the block, including if reading raises an exception.

```python
with open("events.csv", encoding="utf-8") as source:
    header = source.readline()
# source is now closed
```

**Related concepts:** Encapsulates reusable `try`/`finally` patterns and shares the goal of predictable cleanup with Rust’s `Drop`. Unlike garbage collection, the cleanup boundary is explicit in the code.

**Keep in mind:** Read the manager’s contract: leaving a transaction scope might commit or roll back without closing its database connection.

### Newtype pattern

**Tags:** Rust, type safety

**In one line:** The newtype pattern wraps an existing type in a distinct type so the compiler can enforce its meaning.

**Definition:** In Rust, a declaration such as `struct UserId(u64);` creates a separate type whose field stores the underlying value. A function expecting `UserId` cannot accidentally receive an `OrderId`, even if both contain integers. Unlike `type UserId = u64;`, which only introduces another name, a newtype establishes a real type boundary. Keeping the field private also lets you control which operations callers can perform. [Rust book](https://doc.rust-lang.org/book/ch20-03-advanced-types.html#type-safety-and-abstraction-with-the-newtype-pattern)

**Where it shows up:** Database identifiers, measurement units, validated email addresses, and public APIs that hide internal representations.

**Example:** Declare `struct UserId(u64);` and `struct OrderId(u64);`. Given `fn load_user(id: UserId)`, calling `load_user(UserId(42))` type-checks; calling `load_user(OrderId(42))` fails at compile time. The numeric value is identical, but its meaning differs.

**Related concepts:** Builds on encapsulation and nominal typing; type aliases improve naming without creating this separation. Smart constructors can add validation when creating the wrapper.

**Keep in mind:** A wrapper distinguishes meanings automatically; guaranteeing valid contents still requires validation and controlled construction.

### Cache-aside

**Tags:** software architecture, caching

**In one line:** Cache-aside lets application code load missing data into a cache only when someone requests it.

**Definition:** The application checks the cache first and returns the cached value on a hit. On a miss, it reads the authoritative data store, caches the result, and returns it. For updates, a common approach is to commit the database change before invalidating the cached entry. This pattern improves repeated reads but does not guarantee that cached data always matches the database. [Microsoft architecture guide](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside)

**Where it shows up:** Product catalog APIs, profile lookups, and services using Redis alongside a relational database.

**Example:** A request for `product:42` misses Redis, so the service reads PostgreSQL and caches the product for `60` seconds. Later requests reuse it. After changing the price, the service commits the database update and deletes `product:42`; the next request reloads it.

**Related concepts:** Read-through caching puts loading logic inside the cache layer. Time to live (`TTL`) limits how long an entry survives; invalidation removes it explicitly.

**Keep in mind:** Choose an acceptable staleness window before choosing a cache lifetime; expiration and invalidation are part of correctness.

### Covering index

**Tags:** data engineering, databases

**In one line:** A covering index stores every column a particular query needs, potentially avoiding reads from the table itself.

**Definition:** An ordinary index helps locate rows, but the database may still fetch those rows to retrieve other columns. A covering index also contains the values needed for the query’s output. In PostgreSQL, `INCLUDE` adds these extra values without making them search keys. Coverage makes an index-only scan possible, but PostgreSQL may still visit the table to check whether rows are visible to the current transaction. [PostgreSQL documentation](https://www.postgresql.org/docs/17/indexes-index-only-scans.html)

**Where it shows up:** Frequent database lookups that return a few columns, such as fetching customer email addresses by account ID.

**Example:** This index covers the query because it stores both the filter column and the returned column.

```sql
CREATE INDEX customers_account_email
ON customers (account_id) INCLUDE (email);

SELECT email FROM customers WHERE account_id = 42;
```

**Related concepts:** Composite indexes use multiple search keys; included columns provide additional stored values. MVCC visibility checks explain why full coverage does not guarantee zero table reads.

**Keep in mind:** Cover a specific frequent query; adding every column enlarges the index and increases maintenance costs.

### Type narrowing

**Tags:** TypeScript, type safety

**In one line:** Type narrowing lets the compiler determine a more specific type from checks and control flow in your code.

**Definition:** A value declared as `string | number` initially supports only operations valid for both possibilities. After a check such as `typeof value === "string"`, TypeScript allows string operations on the matching path. Early returns also narrow types by eliminating possibilities from the code that follows. Narrowing changes what the compiler knows; it does not convert the value. [TypeScript handbook](https://www.typescriptlang.org/docs/handbook/2/narrowing.html)

**Where it shows up:** Optional configuration values, union types in component props, event handlers, and checks on data typed as `unknown`.

**Example:** The return removes `undefined` from the remaining path, while preserving an intentionally empty string.

```typescript
function label(value: string | undefined): string {
  if (value === undefined) return "Untitled";
  return value.trim(); // value is now string
}
```

**Related concepts:** Type guards supply evidence for narrowing. Discriminated unions make that evidence easy to express through a shared tag. A type assertion such as `as string` asks the compiler to trust you without performing a runtime check.

**Keep in mind:** Check exactly what you mean: `if (value)` also rejects `0` and `""`, which may be valid inputs.

### Interior mutability

**Tags:** Rust, borrowing

**In one line:** Interior mutability lets a Rust value change internal data through a shared reference while preserving memory safety.

**Definition:** Ordinary mutation requires exclusive access through `&mut T`, but specialized containers can provide safe mutation through `&T`. For example, `RefCell<T>` checks borrowing rules at runtime: multiple shared borrows or one exclusive borrow may exist, but they cannot overlap. Its `borrow_mut()` method panics if an incompatible borrow is still active. The rules still apply; this container changes when they are checked. [Rust book](https://doc.rust-lang.org/book/ch15-05-interior-mutability.html)

**Where it shows up:** Test doubles recording calls through `&self`, caches inside otherwise read-only APIs, and mutable nodes shared through `Rc<RefCell<T>>`.

**Example:** A mock implements `send(&self, message: &str)` and stores messages in `RefCell<Vec<String>>`. Calling `self.messages.borrow_mut().push(message.to_owned())` records a message without changing the trait to require `&mut self`. Holding a shared borrow of that vector during the call would cause a panic.

**Related concepts:** `Rc` provides shared ownership; `RefCell` provides checked interior mutation. Thread-safe sharing needs synchronization types such as `Mutex`, rather than sharing a `RefCell` directly.

**Keep in mind:** Keep runtime borrows short, especially across callbacks that might borrow the same value again.
