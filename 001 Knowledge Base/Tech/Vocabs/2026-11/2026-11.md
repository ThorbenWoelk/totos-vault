### Memoization

**Tags:** Python, performance

**In one line:** Memoization remembers a function’s results so repeated calls with the same inputs can reuse earlier work.

**Definition:** A memoized function looks up its arguments in a cache before computing a result. On a cache miss, it runs the function and stores the returned value for later calls. Python’s `functools.lru_cache` provides this behavior for hashable arguments, with a configurable limit on cached entries. It retains references to arguments and results until eviction or explicit clearing. [Python documentation](https://docs.python.org/3/library/functools.html#functools.lru_cache)

**Where it shows up:** Repeated parsing, recursive calculations with overlapping subproblems, and expensive computations whose results depend only on their inputs.

**Example:** Decorate `count_paths(width, height)` with `@lru_cache(maxsize=128)`. After computing `count_paths(20, 20)`, another identical call can reuse the stored result while that entry remains cached. If the function secretly reads a changing global obstacle map, those arguments no longer identify the result completely, and the cached answer may be wrong.

**Related concepts:** Memoization is caching at the function-call boundary. Dynamic programming can use it to avoid recomputing subproblems; LRU chooses which entries to evict.

**Keep in mind:** Cache only when reusing an old result is valid, and include every result-changing dependency in the cache key.

### Send trait

**Tags:** Rust, concurrency

**In one line:** Rust’s `Send` trait means ownership of a value can safely move from one thread to another.

**Definition:** `Send` is a marker trait: it has no methods, but lets the compiler enforce a concurrency guarantee. Rust normally derives it automatically from a type’s components, so ordinary structs containing only `Send` fields usually need no special declaration. A type can be safe to use on one thread yet unsuitable for transfer because it shares internal state without synchronization. For example, `Rc<T>` is not `Send` because its reference count is not updated atomically. [Rust book](https://doc.rust-lang.org/book/ch16-04-extensible-concurrency-sync-and-send.html)

**Where it shows up:** Thread spawning, channels that transfer values between threads, and async executors that move tasks between worker threads.

**Example:** A worker can take ownership of a `Vec<String>` to process its contents. Moving an `Rc<String>` into that worker fails to compile, even if the worker only reads the string: another clone could update the same reference count elsewhere.

**Related concepts:** `Sync` means shared references can cross thread boundaries. `Arc` supports atomic reference counting, but its thread-safety guarantees still depend on the contained type.

**Keep in mind:** Separate transferring ownership from sharing access; they require different guarantees.

### Strangler fig pattern

**Tags:** software architecture, modernization

**In one line:** The strangler fig pattern replaces an old system gradually by moving one capability at a time to a new implementation.

**Definition:** Old and new implementations coexist while a routing layer directs each request to the appropriate one. As capabilities move, the old system handles progressively less work until its remaining dependencies can be removed. Clients can keep using the same interface throughout the migration. The difficult part is often coordinating shared data and internal dependencies, not changing the routing rule. [Microsoft architecture guide](https://learn.microsoft.com/en-us/azure/architecture/patterns/strangler-fig)

**Where it shows up:** Replacing legacy APIs, extracting capabilities from monoliths, and modernizing applications without a single large cutover.

**Example:** A gateway initially sends every request to an old application. After a new catalog service is validated, requests to `/products` go there while `/checkout` still reaches the old application. Later, checkout moves too; the old application can be retired once no clients, jobs, or internal calls depend on it.

**Related concepts:** A facade provides the routing boundary; an anti-corruption layer translates between old and new models. Feature flags can help control which implementation receives traffic.

**Keep in mind:** Define how each migrated capability stops depending on the old system, including its data, before calling that slice complete.

### Materialized view

**Tags:** data engineering, databases

**In one line:** A materialized view stores a query’s results so later reads can reuse them without repeating the full computation.

**Definition:** An ordinary database view stores a query definition; a materialized view also persists its output. This can make repeated joins and aggregations much cheaper to read, at the cost of storage and maintenance work. In PostgreSQL, changes to source tables do not automatically update a materialized view; `REFRESH MATERIALIZED VIEW` recomputes its contents. Readers therefore need to understand how fresh the stored results are. [PostgreSQL documentation](https://www.postgresql.org/docs/current/rules-materializedviews.html)

**Where it shows up:** Reporting dashboards, daily sales summaries, expensive analytical joins, and local copies of data queried from remote sources.

**Example:** A dashboard reads `daily_sales`, which stores revenue grouped by date. Refreshing it at midnight avoids aggregating millions of orders on every page load. An order added at noon will not appear until a later refresh, even though it already exists in the source table.

**Related concepts:** Similar to a cache of query results. Indexes can accelerate lookups within the stored output; incremental maintenance updates only affected results when the database or tooling supports it.

**Keep in mind:** Define the acceptable data age and refresh cost before choosing materialization for speed.

### Satisfies operator

**Tags:** TypeScript, type safety

**In one line:** TypeScript’s `satisfies` operator checks that an expression fits a required type while retaining useful details about its inferred shape.

**Definition:** Writing `expression satisfies Target` asks the compiler to verify compatibility with `Target`. Unlike annotating a variable with that target type, it does not simply replace the expression’s inferred type with the broader target. This helps catch mistakes in object literals while keeping property-specific operations available. The check disappears during compilation and provides no runtime validation. [TypeScript documentation](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html#the-satisfies-operator)

**Where it shows up:** Configuration objects, route registries, theme definitions, and lookup tables whose entries can have different value types.

**Example:** Both values meet the contract, and `title` remains known as a string.

```typescript
const settings = {
  title: "Dashboard",
  retries: 3,
} satisfies Record<"title" | "retries", string | number>;

settings.title.toUpperCase();
```

Changing `retries` to `false` causes a type error. A variable explicitly annotated with that `Record` type would expose `title` as `string | number`.

**Related concepts:** Type annotations declare a variable’s type; assertions with `as` ask the compiler to trust a claimed type. `as const` preserves literal values and marks object properties readonly.

**Keep in mind:** Use `satisfies` to check authored values; validate external data with runtime code.

### Speculative decoding

**Tags:** AI, inference optimization

**In one line:** Speculative decoding speeds up text generation by letting a cheap model propose tokens that a larger model checks together.

**Definition:** A draft model generates several candidate tokens, and the target model evaluates their probabilities in one parallel verification pass. An acceptance rule keeps a valid prefix and corrects the continuation when a proposal is rejected. With the appropriate sampling correction, the original algorithm preserves the target model’s output distribution. This verification checks compatibility with the model’s probabilities, not whether the text is factually true. [Original paper](https://arxiv.org/abs/2211.17192)

**Where it shows up:** Language-model serving systems that aim to reduce generation latency, especially when repeatedly running the target model is expensive.

**Example:** The draft proposes `t1`, `t2`, `t3`, and `t4`. If verification accepts the first two but rejects `t3`, the system keeps that prefix, samples a corrected next token, and discards the remaining draft continuation. Accepted runs let one target-model pass advance multiple tokens.

**Related concepts:** Builds on autoregressive generation and speculative execution. KV caching reuses earlier attention computations; speculative decoding reduces sequential target-model passes.

**Keep in mind:** Measure total latency: a draft model that is too slow or frequently rejected can erase the expected speedup.

### Structural subtyping

**Tags:** Python, type systems

**In one line:** Structural subtyping accepts a type because it provides the required members with compatible types, without requiring a shared parent class.

**Definition:** In Python, `typing.Protocol` describes the methods and attributes that a caller needs. A static type checker can accept an unrelated class that supplies those members with compatible signatures, even when that class never inherits from the protocol. This makes dependencies easier to substitute without changing existing implementations. Protocol annotations do not automatically validate objects at runtime. [PEP 544](https://peps.python.org/pep-0544/)

**Where it shows up:** Library interfaces, dependency injection, test doubles, and adapters around third-party classes you cannot modify.

**Example:** Define a `ByteSource` protocol requiring `read(self) -> bytes`. A function annotated as `load(source: ByteSource)` can accept a custom `MemorySource` with a matching `read` method, even if it has no connection to `ByteSource` in its inheritance hierarchy. A class whose `read` returns `str` does not meet that contract.

**Related concepts:** Duck typing relies on supported behavior during execution; protocols let tools check a declared version of that contract beforehand. Nominal subtyping instead relies on explicitly declared type relationships.

**Keep in mind:** Matching signatures establishes type compatibility, but behavior such as ordering, side effects, and error handling still needs documentation and tests.

### Refutability

**Tags:** Rust, pattern matching

**In one line:** Refutability describes whether a pattern can fail to match a possible value of the type being examined.

**Definition:** A refutable pattern matches only some possible values: `Some(value)` matches an `Option` containing a value but excludes `None`. An irrefutable pattern, such as a simple variable binding, always matches. Ordinary `let` bindings require irrefutable patterns because they provide no alternative path for a failed match. Constructs such as `if let` and `let...else` let you handle that possibility explicitly. [Rust book](https://doc.rust-lang.org/book/ch19-02-refutability.html)

**Where it shows up:** Unpacking optional values, inspecting enum variants, destructuring data, and understanding compiler errors about patterns in bindings.

**Example:** This function exits when the value is absent; after the binding, `name` is available as a string slice.

```rust
fn greet(input: Option<&str>) {
    let Some(name) = input else {
        return;
    };
    println!("Hello, {name}");
}
```

Writing only `let Some(name) = input;` fails to compile because `None` remains possible.

**Related concepts:** Exhaustiveness checking asks whether all branches together cover every case. Refutability asks whether one pattern can miss a case; `let...else` combines destructuring with an early exit.

**Keep in mind:** When a pattern can fail, make the nonmatching path explicit instead of assuming the desired variant is present.
